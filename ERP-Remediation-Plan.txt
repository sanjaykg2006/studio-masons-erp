HOW TO READ THIS DOCUMENT
-------------------------
Each item below has the same shape so it's easy to scan and to brief the
developer:

  * CONCERN     - the problem, in plain terms.
  * WHY IT      - the business risk of leaving it as-is.
    MATTERS
  * THE FIX     - what should actually be built/changed.
  * EFFORT      - rough size: SMALL (hours-1 day), MEDIUM (a few days),
                  LARGE (1-2+ weeks). These are guide figures for one developer.
  * PRIORITY    - P1 (do first), P2 (do soon), P3 (do before heavy real-world
                  use).
  * DONE WHEN   - the simple test that tells you it's finished.

A suggested running order is given at the end.

THE PLAN
================================================================================

--------------------------------------------------------------------------------
#1  FEATURE ROADMAP WITH DATES
--------------------------------------------------------------------------------
CONCERN     No business features exist yet, and there's no published roadmap or
            timeline showing when staff will get usable tools.

WHY IT      Without a roadmap you cannot judge progress, set expectations, or
MATTERS     know when the system will start paying for itself. Effort is being
            spent with no agreed destination.

THE FIX     This is a planning task, not a coding task. Agree with the developer:
            (a) the first 3-4 modules to build and their order,
            (b) a target date for the FIRST module staff actually use,
            (c) what "version 1" must contain to go live.
            Capture it in the existing ERP-Project-Tracker spreadsheet or a
            shared roadmap document.

EFFORT      SMALL (a planning conversation + writing it down).
PRIORITY    P1 - decide this first; it shapes everything else.
DONE WHEN   There is a written, dated roadmap both you and the developer have
            agreed to.


--------------------------------------------------------------------------------
#2  AUTOMATED TESTS (BASIC SAFETY NET)
--------------------------------------------------------------------------------
CONCERN     Nothing automatically checks that the software still works after a
            change.

WHY IT      As the system grows, every change risks silently breaking something
MATTERS     that worked yesterday. Without tests, the only way to catch this is
            manual clicking - which gets skipped under time pressure.

THE FIX     Introduce a test framework (e.g. Vitest) and write a starter set of
            tests around the highest-risk area first: the permissions logic
            (who-can-do-what) and the login guards. Don't aim for 100% coverage;
            aim to cover the parts where a bug would be most damaging. Grow the
            set as each new module is built ("a feature isn't done until it has
            a test").

EFFORT      MEDIUM to set up + a first batch of tests; then ONGOING (small,
            per feature).
PRIORITY    P1 - put this in before building more features, so new work lands on
            a safety net.
DONE WHEN   Running one command executes a suite of tests that pass, and the
            permissions/login rules are covered.


--------------------------------------------------------------------------------
#3  AUTOMATED QUALITY GATE BEFORE CHANGES GO LIVE (CI/CD)
--------------------------------------------------------------------------------
CONCERN     Changes appear to go straight into the live "main" version with no
            automated checks and no second pair of eyes.

WHY IT      A single mistake can reach production unchecked. For a system that
MATTERS     will hold business data, that's an avoidable risk.

THE FIX     Set up a "continuous integration" pipeline (e.g. GitHub Actions) that
            automatically runs on every proposed change and must pass before it
            can be merged: the build, the linter (code style/error checks), the
            type-checker, and the tests from #2. Pair this with a lightweight
            review step - changes go via a short-lived branch and a pull request
            rather than committing straight to main.
            NOTE: this depends on #2 existing to be fully effective.

EFFORT      MEDIUM (one-time setup).
PRIORITY    P1 - pairs naturally with #2.
DONE WHEN   A broken change is automatically blocked from reaching the live
            version, visibly, before it merges.


--------------------------------------------------------------------------------
#4  "INVITE A USER" SCREEN
--------------------------------------------------------------------------------
CONCERN     Adding a new staff member currently requires the developer to run
            database commands by hand.

WHY IT      It doesn't scale, it's error-prone, and it makes routine onboarding
MATTERS     dependent on the developer being available.

THE FIX     Add a user-management section to the existing /access admin screen:
            an "Invite user" form (name + email) that creates the account and
            sends the invite, plus the ability to deactivate/remove a user and
            assign their role - all from the screen, no database access needed.
            The permissions system to gate this already exists, so it slots into
            the current design cleanly.

EFFORT      MEDIUM.
PRIORITY    P2 - high operational payoff; do as soon as the Phase 1 guardrails
            are in place.
DONE WHEN   An administrator can add, role-assign, and remove a user entirely
            from the admin screen without a developer.


--------------------------------------------------------------------------------
#5  AUDIT TRAIL
--------------------------------------------------------------------------------
CONCERN     There's no record of who changed what and when (e.g. permission
            changes, deletions).

WHY IT      For an ERP this is normally a compliance and accountability
MATTERS     requirement. If something is changed or deleted in error - or
            maliciously - there's currently no way to see who did it.

THE FIX     Add an audit log that automatically records sensitive actions (role
            and permission changes, user changes, and later, record deletions)
            with who/what/when. Best enforced at the database level so it can't
            be bypassed. Add a simple read-only "Activity log" view in the admin
            screen for administrators.

EFFORT      MEDIUM.
PRIORITY    P2 - put this in before the system holds real business data.
DONE WHEN   Sensitive changes appear automatically in an activity log showing
            who did what and when.


--------------------------------------------------------------------------------
#6  ERROR MONITORING
--------------------------------------------------------------------------------
CONCERN     If something breaks in production, no one is automatically alerted.

WHY IT      You'd only learn about faults when a staff member complains - by
MATTERS     which point the problem has already affected work.

THE FIX     Connect an error-monitoring service (e.g. Sentry) that captures
            crashes and errors in real time and notifies the developer. This is
            largely a configuration task. (Traffic analytics are already
            installed but only measure visits, not faults.)

EFFORT      SMALL.
PRIORITY    P2.
DONE WHEN   A deliberately triggered test error produces an alert to the
            developer.


--------------------------------------------------------------------------------
#7  KEY-PERSON / "BUS FACTOR" RISK
--------------------------------------------------------------------------------
CONCERN     A single developer holds all knowledge of the system.

WHY IT      If that person becomes unavailable, progress stops and maintenance
MATTERS     becomes difficult or impossible.

THE FIX     Reduce the dependency over time:
            (a) keep written documentation current (the project already has
                good in-code notes and an AGENTS.md - extend this to a short
                "how to run, deploy, and recover" runbook),
            (b) ensure code, database scripts, and access credentials are owned
                by the COMPANY (accounts, repository, hosting) - not a personal
                account,
            (c) introduce the lightweight review step from #3 so a second person
                at least sees changes,
            (d) longer term, plan for a second contributor.

EFFORT      SMALL initially (ownership + runbook); ONGOING thereafter.
PRIORITY    P2 for the ownership/credentials check (do this quickly); P3 for the
            rest.
DONE WHEN   Company owns all accounts and credentials, a recovery runbook
            exists, and someone other than the developer could at least deploy
            and restore the system from the documentation.


--------------------------------------------------------------------------------
#8  DATABASE CHANGES MANAGED PROPERLY
--------------------------------------------------------------------------------
CONCERN     The database structure is updated by hand-pasting scripts into a web
            console.

WHY IT      Manual steps are easy to get wrong, hard to repeat exactly, and make
MATTERS     it difficult to know whether the live database matches what the code
            expects - a growing risk as complexity increases.

THE FIX     Adopt a proper migration workflow using the Supabase CLI: database
            changes are written as version-controlled migration files (these
            already partly exist) and applied with a single repeatable command,
            ideally automatically as part of the pipeline in #3. This makes
            database changes consistent, reviewable, and reversible.

EFFORT      MEDIUM (tooling setup + adopting the workflow).
PRIORITY    P1 - cheap insurance that belongs with the other Phase 1 guardrails.
DONE WHEN   A database change can be applied to any environment with one
            command, with no manual copy-pasting.


--------------------------------------------------------------------------------
#9  MULTI-FACTOR AUTHENTICATION (MFA)
--------------------------------------------------------------------------------
CONCERN     Login is solid and invite-only, but there is no second factor (e.g.
            a code from an app) on top of the password.

WHY IT      A leaked or guessed password is enough to get in. For a system
MATTERS     holding business data, a second factor dramatically reduces that
            risk.

THE FIX     Enable MFA. Two sensible routes:
            (a) turn on Supabase's built-in MFA, or
            (b) connect the planned Microsoft 365 single-sign-on and inherit
                whatever MFA policy your Microsoft tenant already enforces -
                often the simplest option if you're a Microsoft 365 business.
            The codebase is already designed to add the Microsoft sign-on with
            minimal change.

EFFORT      MEDIUM (more if delivered via the Microsoft 365 sign-on).
PRIORITY    P3 - important hardening; schedule once daily operation is stable, or
            bring forward if it ships together with the Microsoft 365 sign-on.
DONE WHEN   Staff must pass a second factor (or your Microsoft 365 policy) to log
            in.


--------------------------------------------------------------------------------
#10 BACKUP & DISASTER RECOVERY
--------------------------------------------------------------------------------
CONCERN     The plan relies entirely on the hosting provider; there's no
            confirmed independent backup or tested recovery process.

WHY IT      Accidental deletion, a bad change, or a provider outage could mean
MATTERS     lost business data with no proven way to get it back.

THE FIX     (a) Confirm and, if needed, upgrade the provider's automatic backup
                settings (point-in-time recovery).
            (b) Set up an INDEPENDENT, regular export of the database to storage
                you control, so you're not solely reliant on the provider.
            (c) Most importantly: actually perform a test restore once, and write
                down the steps. A backup you've never restored is not a backup
                you can trust.

EFFORT      SMALL to MEDIUM (mostly configuration + a one-time recovery drill).
PRIORITY    P2 - do before the system holds real business data.
DONE WHEN   Backups run automatically AND a test restore has been completed
            successfully and documented.


================================================================================
WHAT I RECOMMEND COMMISSIONING FIRST
================================================================================

If you want the highest risk reduction for the least effort, ask the developer
to deliver Phase 1 (#2 tests, #3 quality gate, #8 database workflow) as a single
block of work first. It's mostly one-time setup, it makes every future change
safer, and it's the foundation the operational items in Phase 2 sit on.

Then Phase 2 (#4 invite users, #5 audit log, #6 error alerts, #10 backups) makes
the system genuinely safe to run day-to-day with real data.

Item #1 (the roadmap) should be agreed in parallel right away - it's a
conversation, not a build, and it tells you what all this groundwork is leading
toward.
